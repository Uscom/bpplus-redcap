# Contributing, and forking

Forking is the expected use of this repository, not a fallback. It is an example
collection: a study that copies a module and changes the field names is using it
correctly, and owes nothing back.

This page is mostly about **what to change and what to leave alone** when you do.

---

## If you are forking for a study

### Change the module prefix — but only once, and before you install it

The directory name is the module prefix, and **REDCap keys every project setting
to it**. Renaming it later orphans every setting on every project that used the
old one, with no migration path. Decide at the start:

```
modules/bpplus_data_capture/  ->  modules/mystudy_bpplus/
```

Three things must change together, or the module installs and then does nothing
with no error in any log:

| | |
|---|---|
| The directory | `modules/mystudy_bpplus/` |
| `config.json` `namespace` | `MyStudy\MyStudyBpplus` |
| The class file and class | `MyStudyBpplus.php`, `class MyStudyBpplus` |

REDCap looks for a file named after the **last segment of the namespace**,
containing a class of the same name. CI checks this; if you have taken the code
somewhere without CI, check it by hand.

### Change the fields, freely

Delete what you do not want and add what you do. The module writes what it finds
and reports what it does not in the browser console, so nothing requires the full
set. `fieldNames()` in `js/bpplus-capture.js` is the one place field names are
built.

Two worth keeping whatever else goes — see
[`instruments/bpplus_measurement/field-map.md`](instruments/bpplus_measurement/field-map.md)
for why: the raw XML, and the device timestamp.

### Leave the SDK alone

`sdk/` is a vendored copy. Do not edit it in place — an edit that lives only
there is lost at the next sync and invisible until then. If you need the SDK to
do something different, change it upstream and re-vendor with
`tools/sync-sdk.ps1`; if you cannot, raise it as an issue rather than patching
the copy.

`tools/sync-sdk.ps1 -Verify`, and the module's own `test/smoke.mjs`, both fail
when `sdk/` no longer matches its recorded hash. That check is the whole reason
it exists: two copies of this SDK have already drifted apart while both reported
`SDK_VERSION 1.0.0`.

### Say what it is

Change `config.json`'s `name`, `description` and `authors`, and put your own
study in the README. A module that still says "Uscom Ltd" while doing something
else is confusing for whoever inherits it.

## If you are contributing back

Pull requests are welcome. Two things make them easy to accept.

**Run the checks.** They are what CI runs:

```bash
npm install --no-save jsdom
node modules/bpplus_data_capture/test/smoke.mjs
node tools/build-instrument.mjs          # then check git diff is empty
php -l modules/bpplus_data_capture/BpPlusDataCapture.php
```

**Write the comment that says why.** The code here explains its own reasoning,
particularly where the obvious thing is wrong — the `null` port filter, the
Android transport order, the timestamp separator. Those comments are load-bearing:
each one records a measurement or a failure that cost something to find, and the
next person to "clean it up" needs to meet the reason before the code.

### Things that need discussion first

- **A new module.** Worth agreeing on the prefix before it is written, since it
  is permanent.
- **A change to which fields are written, or what a setting means.** That is a
  major version, and every project pinned to the old one has to be moved
  deliberately. See [docs/versioning.md](docs/versioning.md).
- **Anything in `sdk/`.** It belongs upstream.

## Repository conventions

**Every module folder is exactly what ships.** `config.json` at its root, no
build step that rearranges anything. That is what makes the release ZIP a copy
rather than a construction — and what makes splitting a module into its own
repository later a `git subtree split` and nothing else.

**Generated files are committed.** `DataDictionary.csv` and
`BPplusDemo.REDCap.xml` are both generated by `tools/build-instrument.mjs` and
both checked in, because nobody should have to install Node to download a data
dictionary. CI regenerates them and fails if the result differs, so edit the
tool rather than the output.

**LF everywhere.** See `.gitattributes`. A file written by a tool and the same
file after a checkout differing byte for byte would break the SDK hash on every
machine but one.

**ASCII in anything REDCap imports.** The generator refuses to write a
non-ASCII character into a data dictionary. One curly apostrophe is enough to
turn a field note into mojibake when someone opens the CSV in Excel, and nothing
about that is visible from the machine that wrote it.

**Releases are tagged `<prefix>-v<version>`.** The workflow refuses a tag whose
version does not match the module's `config.json`, because a ZIP whose contents
disagree with its name is the one mistake that reaches a production REDCap and
stays there.
