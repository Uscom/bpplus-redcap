# The BP+ measurement instrument

The instrument the `bpplus_data_capture` module drives.

| File | |
|---|---|
| `DataDictionary.csv` | The fields, to **append** to a project that already has a record ID |
| `DataDictionary-new-project.csv` | The same, with `record_id` in front, for a project with no fields yet |
| `instrument.html` | The button markup, readable — the source of one CSV cell |
| `field-map.md` | What each field holds, and where it comes from in the device |

Both files are generated by `tools/build-instrument.mjs` from one description, so
the dictionary and the demo project cannot disagree about the same instrument.
Edit the tool, not the CSV.

---

## Read this before importing

**REDCap's data dictionary import replaces the entire dictionary.** It does not
add to it. Uploading this CSV to a project that already has instruments deletes
them.

So there are three ways in, and only the first is a plain upload:

### The project does not exist yet

Use [`demo-project/BPplusDemo.REDCap.xml`](../../demo-project/) — **Create a New
Project → Upload a REDCap project XML file**. It contains this instrument, a
record ID, and the measurement instrument already set to repeat.

If you would rather build the project yourself, import
**`DataDictionary-new-project.csv`**, not `DataDictionary.csv`.

> **Which file matters here.** REDCap makes the first field of the first
> instrument the record ID, and forces it to a text field. `bpplus_intro` is the
> descriptive field carrying the Connect and Measure buttons, so importing the
> plain `DataDictionary.csv` into an empty project turns it into a text record
> ID and the buttons are lost. REDCap notes this as an allowable warning about
> cell `D2`.
>
> `DataDictionary-new-project.csv` leads with `record_id`, so the question does
> not arise.

### The project exists

Append rather than replace:

1. **Project Setup → Designer → Data Dictionary → Download the current data
   dictionary.**
2. Open both files in a text editor — not Excel, which will re-quote the HTML in
   the first row and can silently strip the element ids the module needs.
3. Copy every row of `DataDictionary.csv` **except the header** onto the end of
   your own file.
4. Upload the combined file.

Keep a copy of the original before you start. This is the step where work gets
lost.

### You would rather do it by hand

There are 15 fields, and [`field-map.md`](field-map.md) lists them with types
and validation. Add them in the Online Designer, then paste
[`instrument.html`](instrument.html) into a descriptive field **in source mode**.
Slower, and it avoids every import risk above.

## Renaming the fields

Your project probably has naming conventions. The module builds every field name
from one prefix, so this is a setting rather than an edit:

1. Change the prefix in the module's project settings — `bp_`, `visit1_bpplus_`,
   whatever fits.
2. Rename the fields to match. The suffixes (`sys`, `dia`, `csys`, …) are fixed;
   only the prefix moves.

The module reports a field it cannot find in the browser console, once per
measurement, rather than failing — so a partial rename shows up on the first test
record instead of at the end of the study.

## Changing the fields

Delete what you do not want. The module writes what it finds and says so when a
field is missing; nothing requires the full set.

The two worth keeping whatever else goes:

- **`bpplus_xml`** — the device's own result file. It holds every other field's
  value and the cuff trace besides, and it is the only thing that can settle a
  question about a reading years later.
- **`bpplus_datetime`** — the device clock, which is the only record of when the
  measurement was really taken. A REDCap survey timestamp says when the form was
  saved, which is not the same thing.

## Making it a survey

The instrument works as a data-entry form or as a survey; the module hooks both.
Enable it as a survey in the usual way.

One thing to check on your own installation first: whether the module's
`save-xml` action is reachable from a survey page, where the respondent is not a
logged-in user. The measurement does not depend on it — the fields are filled
before the file is attempted — but the XML may not be stored.

## Regenerating

```bash
node tools/build-instrument.mjs
```

Rewrites `DataDictionary.csv` and `demo-project/BPplusDemo.REDCap.xml` from the
field table in the tool. Both are committed, so nobody needs Node to download a
data dictionary.

The generator refuses to write anything containing a non-ASCII character. A
curly apostrophe is enough to turn a field note into mojibake when someone opens
the CSV in Excel, and nothing about that is visible from the machine that wrote
it.
