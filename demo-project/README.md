# The demo project

`BPplusDemo.REDCap.xml` is a whole REDCap project: a record ID, the BP+
measurement instrument, and nothing else. It exists so that "does this work here"
can be answered in one upload rather than by building an instrument first.

Generated by `tools/build-instrument.mjs` from the same field table as the data
dictionary, so the two cannot disagree about the same instrument.

---

## Creating it

**Create a New Project** → *Start project from scratch or begin with a template*
→ **Upload a REDCap project XML file** → choose `BPplusDemo.REDCap.xml`.

It arrives as a classic (non-longitudinal) project with record autonumbering on,
surveys off, and **BP+ measurement already set to repeat** — so a participant can
be measured more than once. Two instruments:

| | |
|---|---|
| **Participant** | The record ID, and nothing else |
| **BP+ measurement** | The buttons and the 14 fields the module fills |

Then have an administrator install and enable **BP+ Data Capture**
([../docs/installing.md](../docs/installing.md)), open **BP+ measurement** on any
record, and press **Connect BP+**.

The project imports on REDCap 15 and arrives ready to use: the measurement
instrument repeats, and record autonumbering is on.

## Turning on the XML file

Off by default, because it needs a field to land in and the field is already
here. To enable it:

1. Module settings → tick **Store the raw measurement XML as a file**.
2. That is all. `bpplus_xml` is already a File Upload field on the instrument.

Worth doing before the first measurement you care about. It is the artefact that
outlives every later question about a reading.

---

## What to change first

The demo is a starting point, and these are the edits nearly every study makes:

**The record ID.** Autonumbering is on. A study with participant IDs of its own
should turn it off and use them — the record ID is sent to the device as the
patient ID, so it ends up inside the result file, which is where it is most
useful.

**The fields you don't want.** Delete them. The module writes what it finds and
reports what it doesn't in the browser console; nothing requires the full set.

**The prefix.** If `bpplus_` clashes with your conventions, rename the fields and
change the **Field-name prefix** setting to match. The suffixes are fixed; only
the prefix moves.

**Repeating instances.** Most studies measure more than once per participant.
Make **BP+ measurement** a repeating instrument — the module handles instances
already, and names each stored XML file with the record and instance.

## What not to change

**The element ids in the descriptive field.** `bpplus-connect`, `bpplus-measure`
and `bpplus-status` are how the module finds its controls. Renaming one gives a
page with dead buttons and no error anywhere.

If you edit that field, do it in **source mode**. REDCap's rich-text editor will
strip attributes it does not recognise, and a stripped `id` looks exactly like a
module that failed to load.

## Using it as a survey

The module hooks the data-entry form and the survey page both, so enabling
surveys works.

One thing to confirm on your own installation first: whether the module's
`save-xml` action is reachable from a survey page, where the respondent is not a
logged-in user. The measurement does not depend on it — the fields are filled
before the file is attempted — but the XML may not be stored.

For a demo, the data-entry form is simpler and shows the same thing.
